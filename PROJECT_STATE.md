## 1. Что это за проект и чего хочет владелец

Проект находится в `C:\Users\Home\Desktop\СЕЙЛС мен`. Это настольное приложение SALES MANAGER FIRST для Windows: найти востребованные товары, выбрать товар или ввести свой, найти возможных покупателей, подготовить персональное коммерческое предложение (УТП), отправить его после решения пользователя и отслеживать ответы.

У приложения три вкладки: **Рынок — Компании — Настройки**. У каждого товара отдельная ветка компаний, предложений и переписки; модельные ветки вроде iPhone и Samsung могут быть отдельными, а рынок объединяет модели в виды товаров. Интерфейс уже использует единую тёмную тему. Нужны понятные действия и сообщения, без лишних элементов, незаметных отказов и тормозов при обычном вводе.

Владелец просил проверять существующий проект, находить и исправлять ошибки, объединить хорошие дополнительные тесты с основными, убрать лишнее и завершать работу с проверенной сборкой. Переписывать всё заново или самовольно добавлять новые функции он не просил.

### Новое исследование рынка

- В интерфейсе нет импорта и нижней строки состояния; индикатор рядом с запуском. Один короткий результат над таблицей. Остальные уведомления находятся сверху. Тёмная тема сохранена.
- Реестр `research/registry.py` содержит 13 адаптеров, 8 с capability market. Знаменатель вычисляется из реестра; числитель — реальные уникальные успешные ответы, сохранённые по run_id в SQLite. Ленты внутри RSS не считаются отдельными инструментами.
- Технические причины — в диагностике, очереди и статусах, не в главном окне. Невыполненные задания означают паузу; исчерпанные задания с менее10 товарами — частичное завершение. Новые разрешённые источники подключаются к следующему плану, выполненная работа не повторяется.
- Comtrade сохранён, но исключён из стандартного рынка и его счётчика. Overpass, Wikidata, MediaWiki и каталоги не относятся к первоначальному поиску товаров.
- План веб-поиска независим для доступных источников и разнообразен по категориям/странам; первый запрос каждого источника не блокируется длинной очередью RSS-статей. RSS расширен до8 лент. Очередь статей продолжается в общем бюджете, вместо остановки после48 страниц.
- GDELT получает запрос к английскому индексу переводов, язык публикаций русский; география спроса всё равно проверяется по тексту. Ограничения сервиса не обходятся.
- Существенная дополнительная ошибка: после извлечения из статьи проверялся полный сайт с посторонними странами из меню. Теперь рыночные источники хранят тот же чистый текст статьи, который извлекался. Полные снимки сайта сохраняются отдельно.
- Исправлены ложное отрицание «упал» внутри «покупали», подтверждённые предпочтения сохраняются без выдуманных цифр; добавлены виниловые пластинки. Показатель или косвенное основание виден в таблице.

Подтверждение ограничено по времени, привязано к ключу, перепроверяется перед поиском; устаревшее обновляется в фоне безопасным account endpoint. Аккаунтная проверка не использует общий кэш; ошибка снимает подтверждение. Поисковые кэши ключевых API привязаны к ключу и исследованию.

Firecrawl с ключом, Exa, Serper и Jina остаются отключёнными, если опубликованные account/billing данные не доказывают бесплатность и запрет автосписаний. В настройках показана отдельная причина; кнопки проверки/переключатели больше не блокируются только из-за наличия ключа. Firecrawl без ключа — только в рамках разрешения сервиса с данного IP. Нельзя объявлять эти неподтверждённые подключения работающими или бесплатными по остатку баланса/галочке.

Ранее часть материалов сборки была вне проекта; по прямому указанию владельца теперь они внутри него.

Для запуска только готового EXE передаётся `dist/SalesManagerFirst.exe`. Исходники с готовым EXE без `.venv` и `build` занимают примерно **54 МБ**.

После завершения процессов проверок и сборки генерируемую `build` можно очистить, но это удалит сохранённые доказательства проверок. Повторные запуски соответствующих тестов, диагностики или сборки создадут новые результаты, а не восстановят прежние доказательства. Удаление `.venv` потребует переустановки зависимостей для разработки. Последний запрос владельца был объяснить размер и подготовить контекст; **в рамках него ничего не удалялось**.

### Выпуск 1.3.7 и объединение тестов

Пользователь поручил объединить хорошие тесты из `agent_quality_tests` с основными, проверить их, исправить ошибки, убрать лишнее и оптимизировать проект. Старые контрактные утверждения не ослаблялись.

### Девять обсуждённых пунктов и выпуск 1.3.8

Позже пользователь прислал девять замечаний, сначала попросил только мнение, затем явно поручил исправить проблемы. Итог по каждому:

1. **API с ключами и ложная галочка.** `_providers`, `billing_blocked_sources`, `test_provider` и `_search` блокировали любые ключи, а UI обещал включение после free_confirmed. Блокировка была намеренной по правилу только бесплатного доступа. В 1.3.8 исправлены интерфейс и подсказки: активация галочкой больше не предлагается, недоступные кнопки заблокированы с объяснением; Firecrawl без ключа остаётся доступен, если разрешает сервис. **Запросы с ключами не включены** — не заявлять обратное. Наличие ключа, остатка квоты или галочки не доказывает отсутствие платных списаний.
2. **Падежи чисел/годов.** В `ai/service.py` добавлены явные семейства известных словоформ, включая год/году и кресел/креслами. Календарная дата отделена от длительности; 20 лет не подтверждают «в 20 году», даже длительность 2026 лет не равна календарному 2026 году. Неизвестные слова остаются консервативно различимыми, разные единицы/масштаб/знак не смешиваются. Это не универсальный морфологический анализатор и не доказательство смысла любого утверждения.
3. **Числа в подписи.** Подпись добавляется программно из настроек. Полная завершающая подпись модели может отличаться пробелами/переносами/пунктуацией только при совпадении всех букв и цифр; затем заменяется точным сохранённым текстом. Изменённые телефоны/номера офиса и использование чисел подписи в неподтверждённых утверждениях отклоняются. Версия промпта и кэша УТП — `offer-v3`.
4. **Content-Type.** `safe_http.py` разбирает MIME без учёта регистра, отдельно от параметров; charset обрабатывает кавычки/пробелы. Нельзя принимать произвольный MIME только потому, что его параметры содержат `text/html`.
5. **SQLite в рабочих потоках.** `Window.submit` передаёт `Store.close` в `Worker.cleanup`. Задача закрывает своё thread-local соединение в том же потоке до уведомления об успехе/ошибке; соединение главного потока сохраняется до закрытия окна. Проверено на повторно используемом потоке после успеха и исключения.
6. **Повторный обход и AI FIT.** `ResearchService._same_ai_evidence` сохраняет прежние FIT и персональную причину при косметических изменениях, только если цитата осталась на том же актуальном URL и полный текущий нормализованный текст подтверждает связь. Исчезнувшие доказательства и новые явные отказы снимают FIT; прежнее решение сохраняется в аудите. Безусловно удерживать старый FIT нельзя.
7. **Исчезнувший email.** Окно УТП объясняет, какой прежний адрес больше недоступен, и требует явного выбора другого. Нельзя автоматически подставлять нового адресата уже подготовленного письма. Другие существующие email доступны, сообщение «у компании нет email» при пустом выборе больше не показывается, старое подтверждение сбрасывается.
8. **Каждая буква товара.** `branch_changed` не записывает повторно одинаковое состояние и не перестраивает таблицу при продолжении ввода. После первого сброса старого выбора следующие буквы не пишут в БД; Enter создаёт/выбирает нужную ветку. Исходное утверждение про большой SQL на каждой букве и существенный износ диска было преувеличением, но лишние вызовы устранены.
9. **IMAP SINCE и локаль.** `mail/service.py` формирует дату с фиксированными английскими месяцами независимо от LC_TIME. Приложение раньше само LC_TIME не меняло, поэтому это был скрытый риск, а не гарантированная ошибка на русской Windows.

Добавлены 72 регрессионных сценария: 31 для чисел/подписи, 27 для HTTP/IMAP, 8 для обновления FIT, 6 для потоков/UI. Общий набор — 636 тестов. Части изменений выполнялись параллельно, полный итоговый набор запускался после объединения; новый EXE соответствует итоговым исходникам.

## 7. Продуктовые и технические ограничения, которые нужно сохранить

- Поисковые источники находят страницы и сведения; Python извлекает факты/контакты, устраняет повторы, управляет очередью и хранит всё в SQLite. GigaChat не выполняет поиск, не получает произвольные инструменты, не исполняет команды и не отправляет письма.
- Источники: открытые RSS, Overpass/OSM, GDELT, Wikidata, MediaWiki, UN Comtrade, пользовательские публичные каталоги и закупки; есть адаптеры Tavily/Serper/Exa/Jina/Firecrawl. Наличие адаптера не означает доступность в сети или разрешение работать с ключом.
- Поиск соблюдает robots.txt, ограничения доступа, CAPTCHA и авторизацию не обходит. Сеть ограничена бюджетами/тайм-аутами; при сбое найденное и очередь сохраняются, повторный запуск продолжает работу.
- Рынок — до 10 разных видов товаров только с источниками и проверкой актуальности/географии. Продажи, закупки, заказы, поисковые запросы и упоминания не складываются. Процент сравнивает только сопоставимую группу по метрике/единице/периоду/стране. Импорт Comtrade показывается отдельно и не выдаётся за текущие продажи.
- Оценки покупателей: FIT, INSUFFICIENT_EVIDENCE, NOT_FIT. Отсутствие товара само по себе не доказывает несовместимость или дефицит. Товару нужна подтверждённая связь с деятельностью, а коммерческая потребность может оставаться гипотезой.
- AI работает с короткими сохранёнными фактами; результаты кэшируются. Подтверждённые токены и неподтверждённая оценка возможного расхода различаются. Неизвестный исход запроса не вызывает автоматического повтора; ручная сверка расхода требует решения пользователя.
- Почта: Gmail — первый вариант нового подключения, также Яндекс и ручной IMAP/SMTP. Используется отдельный пароль приложения, IMAP 993, SMTP 465 или 587 с TLS.
- Перед отправкой обязательны FIT, выбранный email, основание и подтверждение разрешения, отсутствие opt-out, предпросмотр и явное подтверждение пользователя. Неизвестный исход SMTP сверяется, повторно автоматически не отправляется. Реальные письма не посылать ради теста без явного указания владельца.
- Рабочая БД: `%LOCALAPPDATA%\Argon\SalesManagerFirst\sales.sqlite3`. Пароли/API-ключи: Windows Credential Manager, служба `Argon.SalesManagerFirst`. Их не включать в код, SQLite, EXE, Git или отчёты.
- Базу пользователя не пересоздавать и историю не удалять. Для изменения схемы нужны миграции; тестировать их на изолированных данных.
- Не добавлять Excel-экспорт, массовую автоматическую рассылку, поиск поставщиков и прочие несогласованные функции. Не менять исправную архитектуру и интерфейс без необходимости.

## 8. Как проверять и выпускать изменения

Работать из корня проекта в PowerShell, использовать настроенный Python 3.12 из `.venv`, не переустанавливать окружение без причины. В данном PyCharm перед любой Python-командой по навыку python-tools нужно вызвать `get_python_environment` для `main.py` и использовать возвращённый executablePath; сейчас это `.venv/Scripts/python.exe` проекта.

```powershell
$env:QT_QPA_PLATFORM='offscreen'
$env:PYTHONDONTWRITEBYTECODE='1'
.\.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider --junitxml=build/current-tests.xml
.\.venv\Scripts\python.exe tests/quality/runner.py --repeats 5
powershell -NoProfile -ExecutionPolicy Bypass -File packaging\build.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File packaging\verify-exe.ps1
```

Для новой ошибки нужен осмысленный тест воспроизведения и целевые проверки; перед выпуском — общий набор и пересобранный EXE. Не повторять дорогие проверки после успешного прогона без новых изменений или конкретного повода. После изменения только документации функциональные тесты и сборка не требуются.

PyInstaller — основной способ сборки. Скрипт создаёт снимок исходников внутри `build/packages`, ограничивает кэши/временные файлы проекта и копирует готовый EXE в `dist`. Проверка EXE использует свежую тестовую БД и два запуска из `build/smoke-exe/.../standalone`. Дополнительный Nuitka есть, но текущий выпуск им не проверялся. Не запускать сетевые check_*.py автоматически под видом обычных тестов.

Документы или старый отчёт не заменяют чтение текущего кода. Если приложение после этого файла изменится, версию, хеши и результаты нужно проверить заново.
